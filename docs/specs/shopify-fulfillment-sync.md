# Shopify order, payment, fulfillment, hold, and stage notifications

Relay synchronizes real Shopify order payment, fulfillment, tracking, hold state, explicit opt-in consent, and stage WhatsApp Utility notifications bidirectionally with strict tenant isolation, scope-gated API actions, conservative `UNKNOWN` handling, and zero hardcoded merchant rules:

- **Full Shopify fulfillment & payment state**:
  - Sync `OrderDisplayFulfillmentStatus` and fulfillment event milestones (`Unfulfilled`, `In progress`, `On hold`, `Scheduled`, `Partially fulfilled`, `In transit`, `Delivered`, `Restocked`, `Fulfillment not required`) plus `trackingNumber`, `trackingCompany`, and `trackingUrl` via webhooks (`orders/create`, `orders/updated`, `orders/cancelled`, `orders/fulfilled`, `orders/partially_fulfilled`, `orders/paid`, and—when granted `read_fulfillments` / `write_fulfillments` / `write_merchant_managed_fulfillment_orders`—`fulfillments/create`, `fulfillments/update`, `fulfillment_events/create`, `fulfillment_orders/placed_on_hold`, `fulfillment_orders/hold_released`, `fulfillment_orders/progress_reported`, `fulfillment_orders/manually_reported_progress_stopped`) and scheduled/manual GraphQL reconciliation.
  - Display payment state (`financialStatus` and `paymentMethod`) as a first-class status column and filter alongside fulfillment status (`Payment pending`, `Paid`, `Partially paid`, `Authorized`, `Partially refunded`, `Refunded`, `Voided`).
- **Prepaid / non-COD support**: Use tenant-configurable `shopifySync.codGatewayKeywords` (default `['cash on delivery', 'cod']`) to classify COD vs non-COD orders (`isCod`), store Shopify `financialStatus` and `paymentMethod`, and allow `importNonCodOrders` (default `true`) to import non-COD/prepaid orders as `CONFIRMED` without queuing COD confirmation/reminder jobs or inflating COD confirmation totals. If a COD order is marked non-`pending` (`paid`, `refunded`, `voided`), stop/suppress queued COD `CONFIRMATION`/`REMINDER` jobs cleanly.
- **Explicit checkout/customer consent sync (opt-in only)**: Under tenant `shopifySync` (`syncCustomerSmsConsent`, `checkoutConsentAttributeKey`, `checkoutConsentValues`), grant `consent = true` only when Shopify reports explicit SMS marketing opt-in (`subscribed`, read-only and scope-gated via `read_customers`) or a checkout custom/note attribute matches a configured accepted value. Phone collection alone never grants messaging permission, and subsequent sync never clears already-granted consent.
- **Daily routine workspace views + saved custom views**:
  - Built-in views aligned with merchant daily operations: `All orders`, `To confirm`, `Ready to pack`, `Fulfilled · Unpaid`, `Paid`, `Delivered`, `Needs review`, `Cancelled`, paired with Payment and Fulfillment/COD dropdown filters and search.
  - Merchants can save custom views (`settings.orderViews`) per workspace combining active view, payment filter, fulfillment/COD filter, and search term, and delete saved custom views cleanly.
- **Bidirectional Relay → Shopify order & fulfillment actions (`POST /api/orders/:id/shopify-action` & `POST /api/orders/bulk`)**:
  - `mark_paid` -> queues `MARK_PAID` (`orderMarkAsPaid`, requires `write_orders` and Shopify `canMarkAsPaid`; never automatic, single and bulk).
  - `mark_in_progress` -> queues `MARK_IN_PROGRESS` (`fulfillmentOrderReportProgress` on `OPEN`/`SCHEDULED` fulfillment orders; requires `write_merchant_managed_fulfillment_orders`, single and bulk).
  - `reopen` -> queues `MARK_OPEN` (`fulfillmentOrderOpen` on `IN_PROGRESS`/`SCHEDULED` fulfillment orders; requires `write_merchant_managed_fulfillment_orders`).
  - `hold` / `release_hold` -> queues `FULFILLMENT_HOLD` / `FULFILLMENT_RELEASE` (`fulfillmentOrderHold` with `handle: 'relay-hold'` and release restricted strictly to Relay-owned holds; requires `write_merchant_managed_fulfillment_orders`, single and bulk).
  - `fulfill` -> queues `FULFILL_ORDER` (`fulfillmentCreate` on `OPEN`/`IN_PROGRESS`/`SCHEDULED` fulfillment orders with optional courier `company`, tracking `number`, valid `https://` `url`, and `notifyCustomer`, using `AutomationJob.payload`; rejects `ON_HOLD` orders until hold is released; requires `write_fulfillments`).
  - `update_tracking` -> queues `UPDATE_TRACKING` (`fulfillmentTrackingInfoUpdate` on the latest non-cancelled Shopify fulfillment using `AutomationJob.payload`; requires `write_fulfillments`).
  - `mark_delivered` -> queues `MARK_DELIVERED` (`fulfillmentEventCreate` with `status: 'DELIVERED'` on the latest active fulfillment; requires `write_fulfillments`, single and bulk).
  - All non-tag mutating Shopify actions (`MARK_PAID`, `MARK_IN_PROGRESS`, `MARK_OPEN`, `FULFILL_ORDER`, `UPDATE_TRACKING`, `MARK_DELIVERED`) move ambiguous `5xx`/timeouts to `UNKNOWN` rather than retrying blindly; subsequent Shopify webhooks and GraphQL catch-up reconcile confirmed `UNKNOWN`/`QUEUED` jobs when matching order state arrives.
- **Configurable tags & reverse Shopify guardrails**: Store configurable Shopify tag names (`confirmedTag`, `reviewTag`, `cancellationRequestedTag`) and optional fulfillment-hold policies (`autoHoldUnconfirmed`, `holdOnReview`, `holdOnCancellationRequest`, `releaseHoldOnConfirm`, `holdReasonNotes`) per workspace. When optional fulfillment scopes are absent (`write_fulfillments` / `write_merchant_managed_fulfillment_orders`), Relay blocks only those optional actions with actionable instructions instead of breaking existing connections.
- **Customizable stage WhatsApp Utility alerts**: When enabled by the merchant (`settings.dispatchNotifications`), send independent idempotent Utility template messages for `DISPATCH_NOTICE` (`In transit` / `Partially fulfilled`), `DELIVERY_NOTICE` (`Delivered`), `PAYMENT_NOTICE` (`paid`), `IN_PROGRESS_NOTICE` (`In progress`), and `ON_HOLD_NOTICE` (`On hold`) passing only approved Meta placeholders mapped dynamically from tenant settings (`customer_name`, `brand_name`, `order_number`, `courier`, `tracking_number`, `tracking_url`, `total_amount`, plus optional dynamic URL button suffix on dispatch). Enforce `maxMessageAgeHours` freshness, recorded messaging consent or active own-number test mode, `STOP`/`START` opt-out compliance (including cancelling queued stage notices on `STOP`), `config.outbound`, and strict per-order/kind deduplication (`AutomationJob` + `OutboundMessage`).
